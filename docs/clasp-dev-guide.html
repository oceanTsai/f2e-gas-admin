clasp 日常開發指南

假設環境已裝好、專案也接進 repo 了。這份講的是「每天實際開發時怎麼操作」——什麼時候 pull、什麼時候 push、順序為何、多專案怎麼處理。跟著循環走就不會亂。

00先搞懂：程式碼在三個地方

這是最重要的一段。看懂這張圖，後面所有指令就都懂了。

你的 GAS 程式碼，同時存在三個地方：

GitHub
雲端備份・團隊協作
⇄
本地電腦
你的 VS Code（中間點）
⇄
線上 GAS
程式實際執行的地方

三個地方各自的角色：

地方是什麼
GitHub程式碼的歷史備份與團隊協作中心。隊友的改動放這裡。
本地電腦你實際寫程式的地方，也是唯一同時連著另外兩邊的中間點。
線上 GAS程式碼真正執行的地方。Slack 呼叫的、觸發器跑的，都是這裡的版本。

兩條線、兩組指令（別搞混）

本地電腦分別用不同工具連接另外兩邊：

連接用什麼指令
本地 ⇄ GitHubgitgit pull / git push
本地 ⇄ 線上 GASclaspclasp pull / clasp push
關鍵：clasp 和 GitHub 沒有直接關係。 GAS 不知道 GitHub 存在，GitHub 也不知道 GAS 存在。只有你的本地電腦同時連著兩邊，所有東西都經過本地中轉。

pull / push 是什麼意思？

不管 git 還是 clasp，pull = 拉下來、push = 推上去，方向都是相對「本地」而言：

指令方向白話
git pullGitHub → 本地把隊友推上 GitHub 的碼拉下來
git push本地 → GitHub把你的改動推上 GitHub 備份
clasp pull線上 GAS → 本地把 GAS 上的版本拉下來
clasp push本地 → 線上 GAS把本地的碼推上 GAS 去跑
clasp 的 pull / push 是「覆蓋」，不是「合併」。 clasp pull 蓋掉本地、clasp push 蓋掉線上，誰後到誰贏、沒有智慧合併。（git 則有版本合併機制，比較聰明。）所以 clasp 這端更要守紀律：開工先 pull、改完先 push。

01完整開發循環

一個完整回合，把兩條線都照顧到，就是這個順序。

① git pull
拉隊友的碼
→
② clasp pull
拉 GAS 最新
→
③ 改程式
→
④ clasp push
推上 GAS 測
→
⑤ git push
存進 GitHub

兩個 pull 各問不同的地方

① git pull：問 GitHub「有沒有隊友推的新東西？」
② clasp pull：問線上 GAS「有沒有人直接在編輯器改過？」
兩個問的對象不同，所以都要做（尤其多人協作時）。

現階段你一個人開發時： git pull 和 clasp pull 通常會顯示「已是最新、沒東西可拉」——因為都是你自己推的，沒別人動過。做了不會錯，養成習慣就好。等 Pedro、Samura 他們一起改之後，這兩個 pull 就變成必要的開場動作，不然會蓋掉彼此的改動。

02開工前：兩個 pull

坐下來要動某個 GAS 前，先把兩邊的最新版都拉到本地。

# 在 repo 根目錄，先拉 GitHub
git pull

# 進要開發的專案，再拉線上 GAS
cd slackBotProxy
clasp pull

為什麼要先 pull？

因為別人（或你自己在別台電腦、或直接在 GAS 線上編輯器）可能改過。若不先 pull 就開始改、改完 push，會把對方的改動整個蓋掉。先 pull = 確保你站在最新的基礎上。

clasp pull 會覆蓋本地未存檔的改動。 如果你本地有還沒 commit 的東西，先 git commit 或 git stash 存起來，再 pull，才不會被蓋掉。

03本地修改

在你慣用的編輯器（VS Code）裡改，不要在 GAS 線上編輯器改。

程式碼在子專案的 src/ 底下：

slackBotProxy/ ├── .clasp.json └── src/ ├── appsscript.json # GAS 專案設定，一般不用動 └── slackBotProxy.js # ← 在這裡寫你的邏輯
養成習慣：一律在本地改。 本地是「真相來源」，改完 push 上去。若偶爾在線上編輯器改了，下次開工記得先 pull 拉回來，否則本地一 push 就把線上那次改動蓋掉了。

04推上 GAS：push

本地改好，要讓 GAS 實際跑你的新碼，就 push。

clasp push              # 把本地 src/ 推上線上 GAS

push 完，打開 GAS 線上編輯器（或直接觸發你的 Web App / 觸發器），跑的就是你剛推上去的版本。

push 沒反應 / 要強制

若 clasp 因為線上有較新版本而擋下 push，確認你不會蓋掉重要東西後，可加 -f 強制：

clasp push -f           # 強制覆蓋線上（確認過再用）
-f 會無條件蓋掉線上。 只有在你確定線上那版不需要保留時才用。不確定就先 clasp pull 看看線上是什麼，再決定。
如果這個專案有 doPost / doGet（Web App，例如 slackBotProxy）： 光 push 還不夠，要讓對外網址跑到新碼還需「更新部署」。這部分獨立在 Step 07 Web App 部署 說明。

05存進 GitHub：git push

clasp push 到 GAS ≠ 進了 GitHub。這是另一條線，要另外做。

回想 Step 00 的兩條線：clasp push 走的是「本地 → GAS」（讓程式跑起來）；git push 走的是「本地 → GitHub」（做歷史備份與團隊協作）。測試 OK 後，把改動存進 GitHub：

cd ..                   # 回 repo 根目錄
git add .
git commit -m "feat(slackBotProxy): 加入 event 去重"
git push               # 推到 GitHub
兩個 push 徹底分清楚：
• clasp push → 推到「線上 GAS」，讓 Slack / 觸發器跑到新碼
• git push → 推到「GitHub」，做版本歷史與備份
一個管「程式能不能跑」，一個管「改動有沒有留下紀錄」。兩件事，都要做。

06即時同步：watch

密集開發時，不想每改一次就手動 push，可以開 watch。

clasp push --watch      # 監看 src/，一存檔就自動 push

開著 watch，你在 VS Code 每按一次存檔，clasp 自動幫你 push 上去。適合「邊改邊在 GAS 測」的節奏。用完 Ctrl + C 結束監看。

watch 期間別在線上編輯器改。 兩邊同時改會打架——watch 一 push 就蓋掉你線上的手改。要嘛全本地、要嘛關掉 watch。

07Web App 部署（有 doPost 才需要）

只有對外服務型的 GAS 才要看這章。若你的專案有 doPost(e) / doGet(e)（例如 slackBotProxy 被 Slack 呼叫），這章很重要。

核心觀念：push 不等於更新網址

有 doPost 的 GAS 就是 Web App，有一個 /exec 網址對外。最容易踩的坑是：

那個 /exec 網址跑的不是「最新程式碼」，是「某個部署版本」凍結的碼。 所以你 clasp push 改了 doPost，線上編輯器看到的是新碼，但 Slack 打進來還是跑舊碼——因為部署版本還指向你改之前那版。

結論：改完 doPost，push 之後還要「更新部署」，外部呼叫才會跑到新邏輯。

方法 A：GAS 網頁端更新（推薦，最不會錯）

GAS 編輯器 → 右上「部署」→「管理部署作業」→ 點現有部署的鉛筆（編輯）→ 版本選「新版本」→ 部署。網址不變、內容更新。

為什麼推薦網頁端？ clasp 的 deploy 版本管理容易亂（一不小心就生出新網址）。多數人開發 GAS Web App 時：程式碼用 clasp push，更新部署這步在網頁端做，最穩。

方法 B：clasp 指令更新

clasp push                        # 1. 先推程式碼
clasp deployments                 # 2. 看現有部署的 ID
clasp deploy -i <deploymentId>    # 3. 更新「現有」部署（-i 很重要）
一定要帶 -i <deploymentId>。 用 -i 是更新現有部署、網址不變。若直接 clasp deploy（不帶 -i），會生一個全新網址，Slack 那邊設定的舊網址就沒更新到，等於白做。

什麼時候要更新部署？什麼時候不用？

你改了什麼要做什麼
改 doPost / doGet 邏輯（影響外部呼叫）clasp push ＋ 更新部署
只改「手動在編輯器跑」的 functionclasp push 就夠，不用更新部署
只改註解、重構、不影響行為clasp push（+ git 版控）即可
slackBotProxy 的實務節奏： 改完 doPost → clasp push → 到 GAS 網頁端「管理部署作業 → 編輯 → 新版本」→ 回 Slack 頻道 @bot 測一次，確認跑到新邏輯。

08Monorepo 多專案

這個 repo 裝了多個 GAS，clasp 指令認「當前資料夾的 .clasp.json」。

所以操作某個專案前，一定要先 cd 進它的資料夾。clasp 才知道你要對哪個 Script ID 操作：

# 開發 slackBotProxy
cd slackBotProxy
clasp pull
# ... 改 ...
clasp push
cd ..

# 換開發 leaveManagement
cd leaveManagement
clasp pull
# ...
在根目錄直接打 clasp 會出錯或找錯專案。 根目錄沒有 .clasp.json（或找到別的），clasp 不知道對誰操作。永遠先 cd 進子專案。

一次同步所有專案

若在 package.json 設了 push:all / pull:all，可在根目錄一次處理全部（需自行維護這些 script）：

npm run pull:all        # 一次拉所有子專案
npm run push:all        # 一次推所有子專案

09指令速查

日常最常用的就這些。

指令做什麼
git pullGitHub → 本地（開工前，拉隊友的碼）
clasp pull線上 GAS → 本地（開工前，拉線上最新）
clasp push本地 → 線上 GAS（改完推上去讓它跑）
clasp push -f強制推，無條件蓋掉線上
clasp push --watch監看存檔自動推
git add / commit / push本地 → GitHub（存進版本歷史）
clasp open用瀏覽器打開這個 GAS 專案（看執行紀錄、觸發器、手動跑 function 很方便）
clasp deployments列出所有部署版本與其 ID（Web App 更新部署前先看這個）
clasp deploy -i <id>更新現有部署、網址不變（Web App 改 doPost 後用）
clasp login重新登入 / 授權

10狀況排除

開發時最常撞到的幾種。

症狀原因 / 處理
push 後 GAS 行為沒變Web App 的「部署版本」還指向舊碼。到 GAS「管理部署作業」把版本更新為最新。
pull 蓋掉我沒存的改動pull 前沒 commit。養成 pull 前先 git commit / git stash。
clasp 找不到專案 / 報錯沒 cd 進子專案，當前目錄沒有對的 .clasp.json。先 cd 進去。
node:fs/promises constants 錯Node 版本 < 18。確認 node -v 為 22（nvm 已設 default）。
clasp 指令打不動mise activate 未生效。確認 ~/.zshrc 有 eval "$(mise activate zsh)"，重開終端。
push 被擋（版本衝突）線上有較新版。先 clasp pull 看線上內容，確認後再 push 或用 -f。
401 / 未授權憑證失效。clasp login 重新登入。
